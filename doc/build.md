# Сборка, прошивка и тесты

## Сборка и прошивка

ESP-IDF 5.5.x, цель `esp32s3`. Собрано и проверено на 5.5.5; версия, которой
собирали, записана в [`dependencies.lock`](../dependencies.lock). Установка
среды с нуля — [отдельная страница](toolchain.md).

### Версии

Версия прошивки не задаётся руками: ESP-IDF выполняет `git describe --always
--tags --dirty` и кладёт результат в заголовок приложения, откуда его читают и
журнал загрузки, и экран «Об устройстве». Обновляется само при коммите — CMake
следит за файлом ветки и перечитывает версию, когда та сдвинулась.

**Ставьте теги**: без них версия — это короткий хеш, по которому нельзя
сказать, какая сборка новее. С тегом `git tag v1.0.0` она становится
`v1.0.0-3-gabc1234`: имя релиза, сколько коммитов после него и хеш.

```bash
git tag -a v1.1.0 -m "что в этом релизе"
git push origin v1.1.0        # обычный git push теги не отправляет
```

**Новый тег не подхватывается сам.** Версия читается при конфигурации CMake, а
следит она за файлом ветки — коммит его двигает, тег нет. Так что первая сборка
после `git tag` покажет ещё старую строку. Лечится любой переконфигурацией,
проще всего `touch CMakeLists.txt`; при обычной работе это не мешает, потому
что тег ставят на коммит, который и так только что сделан.

Суффикс `-dirty` может отстать. Он считается при конфигурации, а правка файла
ветку не двигает, так что сборка из грязного дерева может показать версию без
него. Для сборки из коммита это неважно.

**У веб-интерфейса версия своя**, потому что он и прошивка пишутся разными
командами. [`tools/stamp_version.py`](../tools/stamp_version.py) кладёт её в
`config/version.json` внутри образа данных при каждой сборке, из той же
`PROJECT_VER`. Устройство показывает обе рядом и говорит, если они разошлись.
Сгенерированный файл живёт только в каталоге сборки, в `data/` его нет.

Собрать другой версией, не трогая git, можно так:

```bash
idf.py -DPROJECT_VER=v1.2.3-test build
```

Значение осядет в кэше CMake — чтобы вернуться к git, удалите строку
`PROJECT_VER` из `build/CMakeCache.txt` (пустое `-DPROJECT_VER=` даст версию
`1`, а не то, что вы хотели).

Проще всего из VS Code: откройте папку проекта, и он предложит поставить
рекомендованные расширения — ESP-IDF и C/C++. Расширение ESP-IDF при первом
запуске само открывает мастер настройки, который скачивает и сам фреймворк, и
компилятор; версию выберите 5.5.x. Дальше `Ctrl+Shift+B` собирает проект, а
остальное лежит в «Terminal → Run Task»: заливка, лог с устройства, хостовые
тесты. На чистую плату — задача «ESP-IDF: First flash (app + data)», она пишет
и прошивку, и раздел данных.

Задачи вызывают [`tools/idf.sh`](../tools/idf.sh), а под Windows —
[`tools/idf.ps1`](../tools/idf.ps1): скрипт находит установленный ESP-IDF, в том
числе поставленный расширением, и активирует его сам — руками запускать
`export.sh` не нужно. Порт определяется автоматически, если плата в системе
одна; если их несколько, укажите нужную через `ESPPORT`.

Ищет он **именно 5.5.5**, а не «что-нибудь из 5.5». На машине, которая хотя бы
раз обновлялась, рядом лежат две версии, и выбор первой попавшейся означал, что
задачи VS Code собирают на одной, а терминал с `export.sh` — на другой; заодно
такая сборка переписывает `dependencies.lock`. Если 5.5.5 не установлена,
берётся любая 5.5.x и скрипт говорит об этом.

`IDF_PATH` при этом **не** перекрывает выбор, и это не упущение: внутри VS Code
её задаёт не человек, а расширение ESP-IDF — оно подставляет в окружение задачи
то, что записано в `idf.currentSetup`. Собрать другой версией намеренно можно
переменной `JRADIO_IDF` с путём к ней; её не ставит никто посторонний. Когда
`IDF_PATH` указывает не туда, куда пошёл скрипт, он пишет об этом строкой в
начале сборки.

Под Windows работают все задачи, кроме «Host tests»: хостовым тестам нужны
POSIX-shell и gcc с санитайзерами, то есть Linux, macOS или WSL.

**Первая сборка ходит в интернет,** и не только за фреймворком. Менеджер
компонентов ESP-IDF скачивает то, что перечислено в `idf_component.yml`
(LVGL, кодеки, драйверы панелей), а компонент littlefs создаёт себе отдельный
venv и ставит в него `littlefs-python` с PyPI — им собирается образ раздела
данных. Дальше всё лежит в `managed_components/` и `build/` и повторно не
качается.

Если сеть моргнёт, сборка падает так:

```
ERROR: Could not find a version that satisfies the requirement littlefs-python==0.15.0
ninja: build stopped: subcommand failed.
```

Сообщение сбивает с толку — человек собирает прошивку и про образ данных в
этот момент не думает, — но лечится повторным `idf.py build`: всё уже
собранное сохраняется, докачивается только недостающее. Если PyPI недоступен
постоянно (корпоративная сеть, прокси), поможет обычная настройка pip —
переменные `PIP_INDEX_URL` и `PIP_PROXY` действуют и на этот venv.

Помогает и pip-кэш, если пакет когда-то уже ставился: он лежит в
`~/.cache/pip` и переживает `fullclean`, который сносит сам venv. Тогда сборка
проходит вообще без сети — `PIP_NO_INDEX=1` и `PIP_FIND_LINKS` с каталогом,
куда положено колесо, действуют так же. Проверено 2026-09-06, когда `pypi.org`
не отвечал ни по IPv4, ни по IPv6, а `files.pythonhosted.org` работал.

Ещё один поход в сеть — только при генерации шрифтов:
[`tools/gen_ui_fonts.sh`](../tools/gen_ui_fonts.sh) зовёт `npx lv_font_conv` из
npm. Обычной сборке это не нужно, готовые шрифты лежат в репозитории.

Из терминала то же самое:

```bash
idf.py set-target esp32s3
idf.py build
idf.py -p PORT flash              # только приложение, LittleFS не трогает
idf.py -p PORT littlefs-flash     # перезаписывает раздел данных целиком
idf.py -p PORT monitor
```

`littlefs-flash` **уничтожает пользовательские данные** — правки плейлиста,
сохранённые сети, настройки устройства и привязку аккаунта Яндекс Музыки:
всё это лежит на том же разделе. Перед запуском сверьте живое состояние:
`curl http://<ip>/api/playlist`, `curl http://<ip>/api/settings` и
`curl http://<ip>/api/yandex`. Настройки после прошивки вернутся к значениям
по умолчанию, а аккаунт придётся привязать заново.

## Тесты

```bash
bash tests/run_host_tests.sh
```

72 набора, ESP-IDF активировать не нужно. Тесты компилируют настоящие
исходники компонентов, а не заглушки, с `-Werror` и санитайзерами. Поэтому
разбор форматов, конечные автоматы и вывод представлений вынесены в файлы без
зависимостей от ESP-IDF — новую логику добавлять туда. Браузерный JavaScript
проверяется под Node с рукописным поддельным DOM, без npm и сборщиков.

## Данные на устройстве

Раздел `littlefs` хранит и статику веб-интерфейса, и пользовательские данные:
`data/www/` (при сборке сжимается в gzip), `data/config/stations.csv`,
`data/config/settings.csv`, `data/radio_img/` с картинками станций, а также
`wifi.json` и `yandex.json`, которые создаёт само устройство и которые в Git не
входят. Всё, что лежит в `data/`, попадает в образ, поэтому картинки станций
переживают `littlefs-flash`; загруженная через браузер и не положенная в
репозиторий — не переживёт. Не добавляйте в репозиторий пароли, токены и
ключи.
